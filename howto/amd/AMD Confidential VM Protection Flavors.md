## AMD Confidential VM Protection Flavors

Here's the full hierarchy of AMD's confidential computing technologies:

---

### 1. **SME** — Secure Memory Encryption
- The foundation. Encrypts main memory using a single ephemeral key generated by the AMD Secure Processor.
- No isolation guarantees — hypervisor still trusted.
- Just protects against physical memory attacks (cold boot, DRAM snooping).
- Key is generated at boot, lives only in the CPU.

---

### 2. **TME** — Transparent Memory Encryption
- AMD's equivalent of Intel's TME; encrypts all memory transparently.
- Often used interchangeably with SME in documentation, but TME is the newer branding on some platforms.

---

### 3. **SEV** — Secure Encrypted Virtualization
- Extends SME to VMs: each VM gets its own encryption key, separate from the hypervisor's key.
- Hypervisor can't read guest memory in plaintext.
- **Weakness**: no integrity protection — a malicious hypervisor can still flip bits (replay/injection attacks), and guest register state is not encrypted.
- ASID (Address Space ID) tags memory pages per-VM.

---

### 4. **SEV-ES** — SEV with Encrypted State
- Adds **CPU register state encryption** on top of SEV.
- On VMEXIT (when the hypervisor takes control), guest register file is encrypted — hypervisor can't read RAX, RIP, etc.
- Introduces the **GHCB** (Guest-Hypervisor Communication Block) protocol for necessary controlled communication.
- **Weakness**: still no memory integrity — content can be tampered with, just not read.

---

### 5. **SEV-SNP** — SEV with Secure Nested Paging
- The current gold standard. Adds **memory integrity** on top of SEV-ES.
- Uses a **Reverse Map Table (RMP)** — a hardware structure that tracks which VM "owns" each physical page. Hypervisor cannot remap or alias guest pages.
- Prevents: replay attacks, memory remapping, aliasing, data injection.
- Enables **attestation**: the guest can get a signed **attestation report** from the AMD Secure Processor (ASP/PSP) proving its measurement (launch digest), VCPU config, platform info, and a guest-provided nonce. This is the core of remote attestation.
- Supports **VMPL** (VM Privilege Levels) — up to 4 privilege rings *within* a guest (VMPL0–3), enabling a trusted layer (like a paravisor or guest firmware) to run at higher privilege than the guest OS.

---

### 6. **SEV-SNP + vTOM** — Virtual Top of Memory
- An optional SNP feature where the guest's encrypted/unencrypted memory split is managed via a virtual top-of-memory boundary rather than the C-bit in page tables.
- Used by some paravisor models (e.g., Microsoft's Hyper-V IGVM-based CVMs).

---

### 7. **SEV-SNP + VMPL-based Paravisor** (architectural pattern)
- Not a separate "flavor" per se, but a deployment model where VMPL0 runs a **paravisor** (e.g., Coconut-SVSM, Microsoft's IGVM paravisor) that mediates device emulation, vTPM, key management for the guest OS at VMPL1+.
- SVSM (Secure VM Service Module) is the emerging standard interface for this.

---

### Practical Note for OCI/QEMU Work
On bare metal work, you're dealing with **SEV-SNP** (Genoa/Milan). 
The QEMU flags you care about are `-object sev-snp-guest` with `policy`, `cbitpos`, `reduced-phys-bits`, and for attestation, the PSP's `/dev/sev-guest` device via the `sev-guest` kernel driver (the `ioctl` path for `SNP_GET_REPORT`).
